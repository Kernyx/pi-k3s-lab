# Pi k3s lab

Учебный single-node Kubernetes на Raspberry Pi 5 (ARM64, 8 ГБ), рядом с уже
работающими Docker/Podman-сервисами. Цель проекта — пройти путь от воспроизводимой
установки до доставки приложения, неудачного релиза и проверенного отката.

**Это лаборатория, не production и не отказоустойчивый кластер.** Пока используется
microSD и SQLite; ценные данные сюда не переносим. Подключённый HDD отклонён после
ошибки чтения в SMART self-test: [разбор](docs/postmortems/001-unhealthy-disk.md).

## Этапы и критерии готовности

1. **Кластер:** повторяемая установка, Node Ready, системные pod'ы готовы,
   проверены DNS/сеть из pod и прежние сервисы хоста.
2. **Приложение:** небольшая домашняя стартовая страница, Deployment/Service,
   readiness/liveness probes, requests/limits.
3. **Доставка:** тесты, сборка ARM64-образа, версия образа связана с коммитом.
4. **Отказы:** rolling update, неудачный релиз, измеренный откат.
5. **Наблюдаемость и упаковка:** метрики приложения, существующий Grafana,
   результаты нагрузки и вопросы для собеседования.

**Этапы 1–4 завершены.** Кластер проверен 2026-09-26, приложение, CI-доставка и откат — 2026-09-27.
ARM64-образ собран в GitHub Actions, скачан Pi из GHCR без токена и запущен по digest.
Обе реплики возвращают Git-коммит релиза; повторный `make up` сохранил их UID и 0 рестартов.
Контролируемый сбой readiness и откат проверены: **746 HTTP-запросов, 0 ошибок,
откат с проверками за 2,461 с**. Метрики приложения и нагрузочный тест — следующий этап.

## Приложение: домашний портал

Стартовая страница со ссылками на сервисы и поиском. Небольшой сервер на Python
без внешних библиотек; две реплики в Deployment, внутренний ClusterIP Service.
Личные адреса задаются отдельным JSON-файлом на Pi и не входят в Git или образ.

Проверено на реальном узле: **2/2 Ready, 0 рестартов, 16–18 MiB RAM на pod**
в снимке без нагрузки. 30 HTTP-запросов через Service попали на обе реплики.
Семь HTTP-маршрутов отвечают, поиск проверен в браузере.
[Как устроен и что проверено](docs/stage-2.md).

## Запуск

Проверено на Raspberry Pi OS / Debian 13, ARM64, systemd, Ethernet `eth0`.
На ноутбуке нужны `make`, Bash, OpenSSH и Python 3 для проверки личной конфигурации;
на Pi — `sudo`, Python 3, curl, SHA-256 и Docker для начальной локальной сборки.
Для выбора CI-релиза по номеру запуска нужен `gh` на ноутбуке.
SSH-ключ и право `sudo -n` на своём узле настраиваются отдельно.
Здесь `my-pi` — **пример**, не адрес настоящего сервера.

Перед началом: сохраните конфигурацию хоста, проверьте свободное место,
отсутствие пересечений с сетями pod'ов `10.42.0.0/16` и Service `10.43.0.0/16`,
и согласуйте перезагрузку с пользователями остальных сервисов.

Если в `/sys/fs/cgroup/cgroup.controllers` нет `memory`:

```sh
make prepare SSH_HOST=my-pi
# Посмотрите изменения /boot/firmware/cmdline.txt и проверьте backup.
ssh my-pi 'sudo systemctl reboot'
```

Подготовка добавляет `cgroup_memory=1 cgroup_enable=memory`, не меняя остальных
параметров. Первая копия файла и её SHA-256 сохраняются в
`/var/lib/pi-k3s-lab/rollback/`. Сам скрипт **не перезагружает** сервер.

После возвращения SSH:

```sh
make up SSH_HOST=my-pi
make check SSH_HOST=my-pi
make smoke SSH_HOST=my-pi
make app-check SSH_HOST=my-pi
make open SSH_HOST=my-pi
ssh my-pi 'sudo k3s kubectl get pods -A'
```

`make open` держит SSH-соединение в текущем терминале. Откройте
**http://127.0.0.1:18080**; `Ctrl+C` закрывает туннели. Порт 13000 дополнительно
проброшен к Grafana на localhost Pi. Port-forward привязан к одному pod;
если тот будет заменён при обновлении, повторите `make open`.

Для своих ссылок скопируйте `app/links.example.json` **вне репозитория** и измените
названия, описания и URL. Не размещайте пароли и токены в URL.

```sh
make configure SSH_HOST=my-pi LINKS_FILE=/private/path/links.json
make deploy SSH_HOST=my-pi
```

Конфигурация сохраняется как `/etc/pi-k3s-lab/links.json` с правами `0600`.
Предыдущая версия сохраняется с проверкой SHA-256. Для каждого содержимого
создаётся immutable ConfigMap с хешем в имени: смена конфигурации меняет
шаблон pod и вызывает rolling update. Старые ConfigMap сохраняются для будущего
отката. Это приватная конфигурация ссылок, **не хранилище секретов**.

`make up` устанавливает/проверяет кластер, затем разворачивает портал.
`make deploy` выполняет только доставку приложения. До выбора CI-релиза используется
локальная сборка; после выбора эти команды сохраняют выбранный registry-релиз.

## CI и доставка ARM64-релиза

Успешный push в `main` запускает тесты/ShellCheck, затем нативную ARM64-сборку в
GitHub Actions и публикацию в `ghcr.io/kernyx/pi-k3s-lab`. Только изменения Markdown/
документации не пересобирают образ. Pull requests не получают права публикации.
Проверьте видимость package после первой публикации: если он private, владелец
один раз меняет её на **public**. В этой проверке package уже был Public и успешно
скачивался анонимно; настройки аккаунта/видимости не менялись. Личные ссылки в образ не входят.

```sh
gh run list --repo Kernyx/pi-k3s-lab --workflow checks.yml
make release SSH_HOST=my-pi RUN_ID=<successful-run-id>
# Или сохранённый артефакт из этого запуска:
make release SSH_HOST=my-pi RELEASE_FILE=/path/outside/repo/release.json
```

Доставка выбирает **digest**, сверяет Git-коммит в артефакте и скачанном образе,
а после rollout проверяет `/api/info` у обеих реплик. `make up` повторно использует
сохранённый релиз. GitHub не получает SSH-ключи или kubeconfig Pi: CI автоматический,
установка — контролируемая команда оператора. [Подробности и ограничения](docs/stage-3.md).

Установка кластера скачивает закреплённый k3s `v1.36.4+k3s1` и установщик из того же тега,
проверяет оба SHA-256, создаёт конфигурацию и стандартный systemd unit.
Установщик не наследует секреты/прокси из окружения и не создаёт команды удаления.
Повторный запуск сверяет файлы и не перезапускает совпадающую установку.
Чужую установку, незавершённую установку или расхождение конфигурации он не затирает.
Это пока **установщик конкретной версии**, не инструмент автоматических обновлений.

Начальный образ приложения собирается Docker на самом Pi из закреплённого по digest
Python-образа, получает тег `src-<хеш исходников>` и импортируется в отдельное
хранилище containerd k3s. На этапе 2 используется `imagePullPolicy: Never`;
registry для bootstrap не нужен. При совпадающем содержимом повторная доставка использует
готовый образ и не меняет pod'ы. Registry-релиз использует `IfNotPresent` и digest,
а `APP_VERSION` содержит полный SHA Git-коммита.

Туннель выделяет удалённый PTY: `Ctrl+C` завершает и SSH, и удалённый port-forward.
Это проверено закрытием/повторным открытием и отсутствием оставшихся слушателей.
[Реальный сбой, который привёл к исправлению](docs/postmortems/002-orphaned-port-forward.md).

Проверка ждёт API `/readyz`, Node Ready и готовности трёх системных Deployment,
показывает `kubectl top nodes`, память systemd-сервиса и свободное место.

`make smoke` запускает временный непривилегированный Job в отдельном namespace:
проверяет DNS Service Kubernetes, внешний DNS, HTTP-запрос к `example.com`,
фактический cgroup-лимит 32 MiB и нулевой swap. Успешный Job удаляется,
неудачный остаётся для диагностики на 5 минут после завершения. Namespace сохраняется.

`make app-check` проверяет rollout и маршруты **через ClusterIP Service**, затем
показывает EndpointSlice и `kubectl top pods`. Это отдельная проверка приложения.

## Проверка отказа и отката

```sh
make drill SSH_HOST=my-pi
# Подставьте имя снимка, напечатанное на вашем Pi:
make rollback SSH_HOST=my-pi SNAPSHOT_DIR=/var/lib/pi-k3s-lab/app-snapshot.EXAMPLE
```

`make drill` намеренно меняет только портал: проверяет rolling update с тем же
образом, затем подключает неверную конфигурацию в отдельном ConfigMap. Новый pod
жив, но не готов; две прежние реплики остаются в Service. После обнаружения
`ProgressDeadlineExceeded` сценарий восстанавливает проверенный снимок и исходный
шаблон. Kubernetes сам не делает откат — его здесь выполняет наш сценарий.

Снимок опыта 2026-09-27: обновление шаблона **16,291 с**, обнаружение сбоя
**30,818 с**, откат с проверками **2,461 с**. Через ClusterIP выполнено **746
HTTP-запросов, 0 ошибок**, без retries; p95 на самом Pi — **1,977 мс**.
Это небольшая проверка непрерывности, не SLA, нагрузочный тест или время
восстановления после падения всего сервера. Личная конфигурация и выбранный образ
не изменились. [Методика и ограничения](docs/stage-4.md),
[разбор намеренного сбоя](docs/postmortems/003-unready-rollout-drill.md).

## Решения и компромиссы

| Решение | Зачем и ограничение |
| --- | --- |
| Один k3s server, SQLite | Меньше компонентов для первого стенда; отказ Pi останавливает весь кластер. |
| Собственный containerd | Docker/Podman остаются отдельными; Kubernetes всё равно меняет маршруты и правила хоста. |
| Без Traefik и ServiceLB | Не занимать порты 80/443 существующих сервисов; ingress добавим только при необходимости. |
| microSD, без важных PVC | Временный носитель для небольшого стенда; ресурс карты и задержки I/O остаются риском. |
| `systemReserved: 2Gi`, `kubeReserved: 512Mi` | Уменьшаем доступную для планирования память; это не изоляция соседних сервисов от всех видов перегрузки. |
| Host zram + pod `NoSwap` | Не меняем swap всей машины; Kubernetes-контейнеры не получают swap. |
| 2 файла логов по 5 MiB на контейнер | Ограничиваем контейнерные логи, но не все записи на карту и не общий journald. |
| kubeconfig `0600`, encryption at rest | Администраторский доступ остаётся у root; шифрование Secret не защищает от root на Pi. |
| Две реплики портала | Основа для rolling update; обе работают на одном Pi, поэтому аппаратной HA нет. |
| Приложение: request 32 MiB / limit 64 MiB, CPU 10m / 250m | Scheduler учитывает request, cgroup ограничивает limit; значения проверены внутри контейнеров. |
| `/readyz` проверяет конфигурацию, `/healthz` — HTTP-процесс | Ошибка ссылок убирает pod из Service, но не вызывает бесполезные рестарты. |
| Python `http.server`, SSH-доступ | Простой учебный сервер; для публичного production-развёртывания нужен другой HTTP-стек и отдельная схема доступа. |

API использует TCP 6443; стандартный Flannel VXLAN — UDP 8472, kubelet — TCP 10250.
Не публикуйте эти порты в интернет. Установщик не управляет роутером, firewall или
Tailscale ACL: доступ из доверенной локальной сети нужно оценивать отдельно.
Anonymous API access отключён. На этом этапе управление выполняется через SSH;
администраторский kubeconfig не копируется в репозиторий.

## Проверки кода

```sh
make test  # unittest, без доступа к Pi и root
make lint  # Bash syntax + ShellCheck
```

Тесты проверяют сохранение boot-параметров, идемпотентность, конфликтующие
параметры, защиту резервной копии, структуру/URL ссылок, HTTP-маршруты и различие
readiness/liveness при неверном JSON, descriptor релиза, соответствие OCI-метаданных,
контроль целостности снимка и подсчёт HTTP-ошибок без скрывающих retries.
Всего 24 теста. Они не заменяют live smoke-test.

## Откат

Откат boot-параметров при необходимости (остановив k3s перед возвратом):

```sh
sudo systemctl disable --now k3s
sudo sh -c 'cd /var/lib/pi-k3s-lab/rollback && sha256sum -c cmdline.txt.sha256'
sudo cp /var/lib/pi-k3s-lab/rollback/cmdline.txt /boot/firmware/cmdline.txt
sudo sync
sudo systemctl reboot
```

Если Pi не загружается, восстановите исходный `cmdline.txt` на загрузочном разделе
с другого компьютера. Для этого копию нужно заранее сохранить **вне Pi**.
Проверена целостность копии; аварийное восстановление с извлечением карты не проводилось.

Чтобы временно убрать k3s, достаточно отключить его unit и в согласованное окно
перезагрузить узел. Остановка unit сама по себе не гарантирует остановку контейнеров
и очистку сетевых правил (`KillMode=process` в upstream unit).
Данные кластера при этом сохраняются. Не запускайте вслепую `k3s-killall.sh` или
`k3s-uninstall.sh`: они меняют сети и удаляют данные; upstream killall также меняет
advertised routes Tailscale. В этой установке эти скрипты намеренно не создаются.

Перед каждой доставкой приложения скрипт сохраняет Deployment, Service и копию
личной конфигурации и выбранного релиза в root-private каталог
`/var/lib/pi-k3s-lab/app-snapshot.*`, проверяет SHA-256. Перед изменением личных
ссылок создаётся отдельная копия. При первом bootstrap предыдущего приложения
ещё нет: сохраняется только конфигурация в `app-before-deploy.*`.

`make rollback` принимает новый JSON-снимок registry-релиза: проверяет его,
сохраняет текущую версию, восстанавливает spec Deployment и проверяет обе реплики
и Service. Затем возвращает сохранённые файлы ссылок/релиза, чтобы следующий
`make up` не вернул отменённую версию. Старые YAML-снимки этапов 2–3 остаются
диагностическими копиями и не подходят этому новому интерфейсу.
Поддерживается сохранённый immutable ConfigMap; изменения Service или потеря
ConfigMap требуют отдельного разбора. Сам k3s и соседние сервисы не откатываются.

## Что плохо и что чиню

- Один узел и microSD — без HA и без обещаний production-надежности.
- Доставка и откат неверной конфигурации проверены; метрики приложения и нагрузочный тест ещё впереди.
- Проверен rollout с тем же образом, не миграция данных или отказ Pi; автоматического rollback-controller нет.
- Локальные образы, старые ConfigMap и снимки доставки пока сохраняются; политику очистки ещё нужно добавить.
- Нет проверенного восстановления состояния самого k3s. Лаборатория должна
  пересоздаваться; секреты и уникальные данные не хранить.
- Существующие мониторинг и уведомления зависят от того же домашнего хоста;
  независимый внешний heartbeat ещё нужен.
- Установка проверена на одном ARM64-хосте. Автообновление и миграции не реализованы.
